## 一句话结论

这篇文章最值得保留的判断是：AI 记忆要真正可用，必须同时具备“规则文档 + 自动执行机制 + 回复前主动调用”三件事。

## 摘要

文章记录了一个 OpenClaw 助手从“几乎没记忆”到“可自动记忆并调用”的改造过程。作者先发现 group-memory skill 只有说明文档、没有自动执行代码，于是自己写了 Python 脚本做重要性评分和记忆更新。随后通过 OpenClaw Hook 把脚本挂到 `message:sent` 事件，实现回复后自动写入记忆。最后又补上“回复前读取群记忆”的调用环节，形成完整闭环。核心价值不是功能本身，而是把“记得住、用得上”做成稳定流程。

## 关键信息

- 仅有 `SKILL.md` 规则不足以形成能力，缺少自动执行时依然会退化成“手工查记忆”。
- 通过 Hook 监听消息事件，可以把“记忆更新”从手动动作变成系统级自动动作。
- 记忆闭环的关键路径是：收到消息读取记忆 -> 生成回复 -> 发送后更新记忆。

## 正文整理

### 背景

起因是群里一句“你没有 group memory 吗？”。作者检查后发现记忆目录是空的，说明系统并没有稳定执行群记忆写入。进一步阅读 skill 说明发现，规则定义是完整的，但执行机制缺位。

### 核心内容

作者把问题拆成三个阶段推进：

1. 手搓脚本  
编写 `analyze_and_update.py`，按关键词给消息打重要性分并写入记忆，先验证“逻辑可行”。

2. 接入 Hook 自动化  
新建 `group-memory-hook`，用 `HOOK.md` 定义触发事件，用 `handler.js` 在 `message:sent` 后调用 Python 脚本，实现“每次发送后自动更新记忆”。

3. 补齐调用链路  
在回复前强制读取 `memory/groups/{chat_id}.json`，避免“只记录不调用”。

### 值得保留的方法或结论

文章沉淀出的通用方法：

- 先验证最小可行脚本，再接入框架生命周期事件。
- 对 Agent 能力不要只看“会不会做”，要看“会不会自动做”。
- 记忆系统要区分“写入能力”和“调用能力”，缺任何一个都会掉链子。

作者最后给出的闭环表达很清晰：  
收到消息 -> 读取群记忆 -> 生成回复 -> 发送后自动更新记忆。

### 后续可行动项

- 给 `importance` 评分增加可配置阈值，便于不同群场景复用。
- 在日志中增加“本次记忆是否命中调用”的可观测字段，降低黑盒感。
- 把这套“文档 -> 脚本 -> Hook -> 调用链路”的流程抽成团队可复用模板。
