# 当 AI 开始"左脚踩着右脚往上爬"……

作者：大爷

发布时间：2026-03-07 15:38

来源：[微信公众号原文](https://mp.weixin.qq.com/s/pyt-QmEC3L3SCYWsOg5p3g)

标签：OpenClaw / AI 协作 / Agent / 交互设计 / 工具体验

## 一句话结论

这篇文章最值得保留的判断是：AI 系统的进步不只体现在“能做更多事”，还体现在它能根据反馈直接优化协作流程本身。

## 摘要

作者在使用 OpenClaw 搭建的 AI 助手“小龙”时，接连遇到白名单、搜索 API、命令触发和重启反馈等问题。最不舒服的点并不是某个能力缺失，而是系统在配置和重启时太黑盒，用户无法确定是否成功。一次明确反馈之后，助手没有只做解释，而是当场调整了自己的操作流程：先预告、再执行、最后回报。这让作者意识到，AI 最值得关注的变化之一，是它开始在互动中改进协作本身。

## 关键信息

- 真正影响体验的不是单个 bug，而是“系统做了事，但用户感知不到”的黑盒感。
- 涉及重启、配置、切换能力的操作，必须从静默动作改成显式交互。
- AI 协作的上限，取决于系统是否能把用户反馈转成稳定的流程改进。

## 我的笔记

- 我认同的点：这篇文章抓到了 Agent 系统里最容易被忽略的一层，不是模型能力，而是副作用操作的可感知性。
- 我想继续验证的点：这套“先预告、再执行、后反馈”的规则，是否应该成为 OpenClaw 工具调用的默认规范。
- 与现有笔记的关联：它和 Aliyun-Bridge 一样，都说明一套系统一旦跨越“试一下”进入“长期使用”，反馈透明度就会变成一等公民。

## 正文整理

### 背景

作者这两天一直在调 OpenClaw 助手，包括：

- 让它在群聊里自由发言
- 补图片生成能力
- 配搜索 API
- 调整 Telegram 命令和 skill 触发关系

这些问题单看都不算大，但在持续配置中，作者明显感受到系统交互成本很高。

### 核心内容

最关键的案例发生在 2026 年 3 月 6 日晚。作者给助手配置了搜索 API，系统随后重启，但：

- 重启前没有提示
- 重启中没有状态
- 重启后没有主动反馈

作者只能靠发一句 “Ping” 去确认系统是不是还活着。

这暴露出的核心问题不是“功能没配好”，而是整个交互链路太黑盒了。于是作者直接指出这个问题，希望系统优化这种协作体验。

助手随即给出新的交互方式，并马上在真实操作里验证：

- 执行前先说明要做什么
- 提前提示会触发 Gateway 重启
- 告知大致耗时
- 操作完成后主动回来汇报结果

作者让它先删除 Kimi API 配置，再恢复配置，整个流程都按新模式执行。

### 值得保留的方法或结论

文章把这次折腾沉淀成了几条很实用的原则：

1. 命名要一致，否则用户记不住 skill 名和触发词。
2. 网络环境必须纳入设计，否则“配置正确”不代表“服务可用”。
3. 任何重启都必须有反馈，否则用户只能盲等。
4. 配置应该尽量透明，让系统从黑盒变成玻璃盒。

这里最值得保留的，不是某个配置细节，而是一个更高层的判断：

- AI 不只是执行指令
- AI 还可以通过对话优化自己的协作方式
- 用户反馈如果能直接转成流程规则，系统会越用越顺

### 后续可行动项

- 可以把这篇文章抽成一条 OpenClaw 设计规范：所有副作用操作默认采用“预告-执行-反馈”三段式。
- 可以在未来的工具链里补一个统一的操作结果模板，降低黑盒感。
- 如果后面再出现类似案例，可以单独整理“AI 协作体验设计”专题。
